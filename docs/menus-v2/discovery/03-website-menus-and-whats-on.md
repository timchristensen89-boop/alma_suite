## 4. Build / deploy

- **Framework:** Next 16.2.4 App Router with `next dev --webpack` / `next build --webpack` (`apps/web/package.json:6-7`), `turbopack.root` set in `next.config.ts:9-11`. No `images`, `rewrites`, `headers`, `output` or ISR config — `next.config.ts` holds only `redirects()` (`:12-74`: legacy venue domains via `lib/legacy-redirects.ts`, `www`→apex 301, `/events*`→`/whats-on`, `/menus`→`/menu`, `/unsubscribe`, Squarespace leftovers).
- **Rendering mode per route (from code, no explicit `dynamic`/`revalidate` exports anywhere — grep):** `/menu/[venue]` is statically prerendered via `generateStaticParams` (`app/menu/[venue]/page.tsx:20-22`); `/whats-on`, `/alma-avalon`, `/st-alma`, `/venues`, `/catering`, `/` are static (pure data modules); `/menu` and `/book` read `searchParams` so render per request (`app/menu/page.tsx:28-29`, `app/book/page.tsx:20-23`); all `/print/*` read `searchParams` (per request); `/gift-cards-alma` fetches the suite with `cache: "no-store"` (`lib/alma-gift-cards.ts:47-54`). The only `revalidate` in the repo is inside the Google Reviews route handler's outbound fetch (`app/api/google-reviews/routes.ts:63`, 6 h). Sitemap is generated at build with a single timestamp (`app/sitemap.ts:8`).
- **Hosting:** Vercel. Evidence: `@vercel/analytics` dependency (`package.json:14`, not actually rendered — only GA gtag in `app/layout.tsx:27-35,91-110`, default id `G-W5L00F6W5L`), `.vercel` gitignored, and the explicit statement "The site deploys from the working tree (vercel CLI), so without this gate the route would go live with the next unrelated deploy" (`app/vouchers/nbws/page.tsx:61-65`). There is **no `.github/` directory, no CI workflow and no `vercel.json` for `apps/web`** (only `apps/order/vercel.json` with a cron). So a commit to `main` does not by itself deploy; someone runs the Vercel CLI from a checkout.

## 5. Integration options for V2

**Option A — website reads from the suite API at request/ISR time.**
- Needs new **unauthenticated read endpoints** in the suite (every path not in `apps/api/src/lib/public-paths.ts:14-76` 401s), e.g. `/api/public/menus/:venueSlug`, `/api/public/menus/:venueSlug/:menuSlug{.json|.pdf}`, `/api/public/promotions/:venueSlug`. The suite already stores the published PDF bytes per version (`MenuVersion.pdfData/pdfByteSize/pdfGeneratedAt`, `packages/db/prisma/schema.prisma:6343-6347`) and a `GET /api/menus/versions/:versionId/pdf` (`routes/menus.ts:58-61`, currently session-only), and renders with the same headless-Chrome engine the website used (`apps/api/src/lib/menu-pdf.ts:10-19`).
- Website side: convert `MenuPageClient` to receive data as props from a server component (today it imports the static module inside a `"use client"` file, `MenuPageClient.tsx:1,6`), fetch with `fetch(url, { next: { revalidate: N, tags: [...] } })`, and add a `revalidateTag`/`revalidatePath` route the suite calls on publish (on-demand ISR works on Vercel; nothing in the repo prevents it). PDFs can be proxied (`/menus/[venue]/[slug].pdf` route handler streaming the suite bytes with a Content-Disposition filename) or linked directly to the API host.
- Trade-offs: single source of truth, instant publish, promotions can be joined to What's On items; but a runtime dependency on `api.almagroup.com.au` (mitigate with ISR cache + last-good fallback — the current committed data could remain the fallback), public endpoints need rate limiting and must expose only published snapshots, SEO requires server rendering of menu text, and deploys stay decoupled from content (good) while the CLI deploy model stays as is.

**Option B — the suite pushes files (extend the existing `website-menu.service` pattern).**
- Commit `apps/web/data/menus.ts` (+ a `whats-on`/promotions data file + PDFs under `public/menus/`) to GitHub; then trigger a deploy.
- Trade-offs: site stays fully static with zero runtime dependency and content is versioned in git; but today **nothing deploys on commit** (CLI from working tree, no Git integration, no deploy hook) so the push is incomplete without adding Vercel Git integration or a Deploy Hook; the Contents API is one file per commit (multi-file consistency needs the Git Trees API); binary PDFs bloat the repo (already 4.2 MB in `public/menus`); the generated TS must be kept in lock-step with the site's types (it has already drifted: `diet`, setMenus, images); conflicts with hand edits (`data/menus.ts` was hand-edited 2026-09-24 after the service was written); minutes of latency.

**Option C — hybrid:** suite publishes JSON + PDFs to object storage (or keeps serving them) and the website uses ISR with an on-demand revalidate webhook; or the suite commits data but the site reads PDFs from the API. This keeps the site resilient (cached static output) while removing manual PDF copying.

**Stable identifiers** (so renames do not break URLs or anchors):
- Venue: standardise on the suite's `Venue.slug` (`schema.prisma:4268`, unique) which already equals the website's `VenueSlug` `alma-avalon|st-alma` (`data/venues.ts:3`) and the template `venueSlug` values in `packages/shared/src/menu-render.ts:53,63`. The website would need a mapping layer for its other codes (`avalon|freshwater`, `avalon|st_alma`, `alma_avalon|st_alma`, `avalon|stalma`).
- Menu: the suite's `Menu` is identified by `id` (cuid) with `@@unique([venueId, name])` (`schema.prisma:6306-6323`); `name` is user-editable (PR #313 adds rename), so public URLs/paths must not embed it. Add an immutable `slug` (or `publicKey`) per menu plus a `kind` (food / drinks / functions / happy_hour / bottomless / special / private_event) so the site can address `/menu/{venueSlug}` and `/menus/{venueSlug}/{menuSlug}.pdf`; use `MenuVersion.id` only as a cache-buster (`?v=`). Keep the current public filenames (`alma-avalon-menu.pdf`, `alma-avalon-drinks.pdf`, `st-alma-menu.pdf`, `st-alma-drinks.pdf`, `alma-functions-menu.pdf`) as aliases/redirects — they are linked from `data/menus.ts:34-35,183-184` and `catering/page.tsx:209` and likely from Google/OpenTable.
- Items: the suite's `MenuItem.dishKey` (`schema.prisma:6398`) is the stable per-dish key across versions — the right hook if the site ever deep-links or highlights dishes (staff picks today are free text in `data/venues.ts`).
- What's On: the website's event ids `happy-hour-avalon`, `bottomless-lunch-avalon`, `taco-wednesday`, `taco-tuesday`, `bottomless-lunch-st-alma` are DOM anchors (and would be the obvious promotion slugs); a promotion record should carry an immutable slug and a `venueSlug`, and link menus by menu id/slug, never by name.

## Cross-cutting findings for V2 planning
1. Three parallel menu datasets already exist in this repo alone: web (`data/menus.ts`), A4 print food (`app/print/_food/menus.ts`), and literal JSX drinks binders — plus the suite's `MenuDocument`. Prices currently agree (both bumped +$1 in `1695400`), but there is no mechanism keeping them aligned.
2. Set-menu vocabulary differs by surface: web + print food say Grazing 49 / Feasting 79 / Agave pairing 45; `/catering` says Alma Table $125, Bottomless $99, Grazing $49, "Six course, Trust the Chef" $79, House drinks package $49; the push script/service default St Alma to "Trust our chef 79 pp".
3. Promotions on What's On (Taco Wednesday $5 tacos/$15 margaritas, Taco Tuesday $5 tacos, Happy hour, Bottomless $99 pp) have no menu artefact on the site; the two bottomless A5 PDFs (2025 InDesign) are orphaned.
4. The home page duplicates both menu highlights and the What's On agenda in local arrays (`app/page.tsx:78-83,112-118`) rather than reading the data modules; `homeAgenda` is dead.
5. Both automated writers of `data/menus.ts` (website script and suite service) would delete the `diet` field and reset images/setMenus.
6. `MenuPageClient`'s venue toggle changes content without changing the URL, so `/menu/st-alma` can display the Avalon menu after a click.
7. Deploys are manual (Vercel CLI from a working tree); no CI exists in this repo. Any push-based integration needs a deploy trigger to be complete.
