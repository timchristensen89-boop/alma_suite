## 4) Asset storage patterns, code references, limits — and what to reuse

**A. Bytes-in-Postgres ("house pattern"; schema comment 2354-2355: "no object store is wired")**
- `GiftCardArtwork` (2357-2364): `giftCardId @unique, mimeType, data Bytes`; own table "so the blob never rides along on GiftCard list queries". Cap `CUSTOM_ARTWORK_MAX_BYTES = 4MB` (`gift-card.service.ts:196-202`). - `HandbookDocument` (4154-4172): `title, description?, fileName, mimeType, sizeBytes Int, data Bytes, venue?, sendOnOnboarding, position, uploadedByStaffId`. Upload is a JSON body carrying a **base64 data URL** (`handbook-document.service.ts:45-60 decodeDataUrl`), MIME allowlist pdf/png/jpeg/webp/heic/gif (25-32), `HANDBOOK_MAX_FILE_BYTES = 4MB` (39) chosen because `express.json` is 6mb and base64 inflates by a third (35-38). Served authenticated `GET /api/handbook-documents/:id/file` (`routes/handbook-documents.ts:23-34`) with `Content-Type` + `inline` disposition, **no Cache-Control**. Manager-only writes (36-58).

- `MenuVersion.pdfData Bytes?`, `pdfByteSize Int?`, `pdfGeneratedAt` (6343-6346; comment cites HandbookDocument/GiftCardArtwork). Written inside the publish transaction (`menu.service.ts:848-856`, `pdfData: new Uint8Array(rendered.pdf)`), read by `getVersionPdf` (896-905; filename `${venue.slug}-${menu.name}-v${n}.pdf`), list/summary selects `pdfByteSize` only (81-82, 122-123). No byte cap; the publish gate instead enforces exactly one page (821-828).
- Gift-card **settings images**: stored as `data:image/...` strings inside the gift-card settings JSON (`INLINE_IMAGE_FIELDS = ['heroImageUrl','artworkUrl']`, `gift-card.service.ts:531-558`) and rewritten for clients to `${env.publicApiUrl}/api/gift-cards/assets/:field/:fingerprint` (sha256 prefix 16 of the content). Served `GET /api/gift-cards/assets/:field/:fingerprint` (`routes/gift-cards.ts:84-97`) with **`Cache-Control: public, max-age=31536000, immutable`** — the one fingerprinted/immutable public asset route in the suite. `env.publicApiUrl = API_PUBLIC_URL ?? API_URL` (`env.ts:124`).

**B. URL-only registry — `MarketingContentAsset`** (2161-2188) + join `MarketingContentPostAsset` (2219-2231: `postId, assetId, sortOrder`, unique pair): `venue String, title, description?, assetType IMAGE|VIDEO|DOCUMENT, mimeType, fileName, fileSizeBytes, storageProvider LOCAL|CLOUD_STORAGE|EXTERNAL_URL (default EXTERNAL_URL), storagePath?, publicUrl?, thumbnailUrl?, width?, height?, durationSeconds?, status DRAFT|READY|ARCHIVED, tags Json, source UPLOAD|IMPORT|GENERATED` (enums 306-328). **No bytes column.** `validateContentAssetPayload` (`marketing.service.ts:1131-1159`) rejects any provider other than `EXTERNAL_URL` ("Direct content uploads are setup required") and requires `publicUrl`. `contentUploadConfig` (2488-2495) advertises `mode: 'external_url'`, accepted MIME `image/jpeg,png,webp, video/mp4,quicktime, application/pdf`, `maxFileSizeBytes 250MB` (aspirational). **C. Google Cloud Storage signed URLs — stock-api only.** `/home/user/alma_suite/apps/stock-api/src/services/uploads.service.ts`: bucket `UPLOADS_BUCKET` default `alma-uploads` (private), `signUploadUrl` (V4 PUT, 15 min, `x-goog-content-length-range 0..5MB`, image MIME only, folders `deliveries|gift-cards|compliance|marketing`), `signReadUrl` (1 h), routes `POST /api/uploads/sign|view`, `DELETE /api/uploads` (`routes/uploads.ts`). `@google-cloud/storage` is a dependency of stock-api only (`apps/stock-api/package.json:17`); the suite API has zero `gs://`/signed-URL usage.

**D. Render-on-request PDFs** — financial documents: `GET /api/invoices/:id/pdf` (`routes/financial-documents.ts:110-120`) renders every call via `renderFinancialDocumentPdf` (`financial-document.service.ts:357-375, 915-917`); nothing stored.

**E. Static bundled render assets** — fonts (Avenir LT Std ×4 OTF, Cormorant Garamond Italic ×2 woff2, Manrope) and logos (`avalon-logo.png`, `stalma-logo.png`) in `/home/user/alma_suite/apps/api/assets/menus/{fonts,images}`, loaded once and inlined as data URIs (`lib/menu-assets.ts:48-84`; refuses to render if any is missing), registered in `MENU_FONT_FILES`/`MENU_LOGO_FILES` (`packages/shared/src/menu-render.ts:397-410`). **Duplicated** in `/home/user/alma_suite/apps/menus-web/public/{fonts,images}` for the editor preview, which loads them from `window.location.origin/fonts/...` (`apps/menus-web/src/components/MenuPreview.tsx:24-36`). Not an asset pattern despite the name: `TemperatureAsset` (3038-3057) is the fridge/freezer register (name, venue, min/max °C, integration ids) — no binary data; grep of `routes/temperatures.ts` and `temperature.service.ts` for photo/image/base64 is empty.

**Recommendation for V2**
- *Generated PDFs (A5 cards, website food/drinks/functions PDFs):* keep bytes on `MenuVersion.pdfData` exactly as today (one PDF per published version, lists already avoid the blob). Add a **public, fingerprinted read route** modelled on `/api/gift-cards/assets/:field/:fingerprint` (immutable cache; fingerprint = hash of bytes or `versionId`) so the website and QR can link to the current PDF without authentication, instead of the private `/versions/:id/pdf`. The publish gate (`menu.service.ts:821-828`, "must fit on one A4 page") and the fixed A4 viewport (`menu-pdf.ts:123`) must be relaxed per template for A5 and multi-page.
- *Promotion images:* no suitable model exists. Recommend a new Bytes table in the HandbookDocument/GiftCardArtwork mould (data-URL JSON upload, MIME allowlist, ~4MB cap under the 6mb JSON limit, `sizeBytes` + `mimeType` + `venueId`), served through the same fingerprinted immutable route. `MarketingContentAsset` is usable only as a URL registry (no bytes, uploads "setup required"); the GCS bucket exists only in stock-api and would need the SDK, credentials and a cross-service contract added to the suite API. If images above ~4MB are needed, the precedent for a bigger body is `express.raw` with its own limit mounted before `express.json` (`server.ts:93-99`).

## 5) Auth / permission model for menus

- App id: `almaAppIdSchema` includes `'MENUS'` (`packages/shared/src/index.ts:172`).
- `authMiddleware` (`auth-middleware.ts:148-265`): session from cookie `env.sessionCookieName` or `Authorization: Bearer`; `VENUE_DEVICE` accounts (shared iPads) may read but write only under `/api/device` (193-195), optionally elevated by a staff PIN (162-181); read-only accounts (`isReadOnlyAccount`, 47-54) cannot write; `/api/menus` requires an ENABLED `MENUS` or `COMPLIANCE` grant or `isAdmin` (241-244 via `hasEnabledAppAccess` 17-21; an account with **no** app rows is treated as COMPLIANCE-enabled, 19).
- Non-managers (`isManager` 27-30: role ADMIN/MANAGER or isAdmin) may only write what `isStaffWriteAllowed` lists; for menus (91-104): `POST /api/menus`, `PATCH /api/menus/:id`, `POST /api/menus/:id/(archive|unarchive)`, `POST|PUT|DELETE /api/menus/:id/draft`, `/draft/preview`, `/draft/publish`, `/draft/items/copy-to`, `POST /api/menus/versions/:id/restore`.
- `requireMenuPublisher` (`routes/menus.ts:25-31`) → `canPublishMenus` (`packages/shared/src/menus.ts:805-825`): true for `isAdmin`, role `ADMIN`/`MANAGER`, `roleTitle` containing "head chef", a `MENUS` grant at role MANAGER/ADMIN, or a `MENUS` USER grant with `permissions.menusPublish === true`; false for `VENUE_DEVICE`. Applied to `POST /` (create), `PATCH /:menuId` (rename), archive/unarchive, `POST /:menuId/draft/publish`. Reading, drafting, saving, discarding, restoring, copying and preview are open to anyone the middleware admits (route header comment 8-24).
- Staff-app toggle: `/home/user/alma_suite/apps/staff-web/src/App.tsx:336-338` defines `{ key: 'menusPublish', label: 'Publish menus' }` under MENUS; role presets at 238 and 252 give manager/head-chef presets `MENUS: MANAGER + menusPublish`.
- **Website publishing is gated differently**: `/api/website/*` needs `requireManager` plus COMPLIANCE access (middleware fallthrough 255-257). A head chef with MENUS-only access can publish a PDF but not the website.
- **No venue scoping**: `menuService.home()` lists every venue's menus for anyone admitted.
- **Venue identity**: `Menu.venueId → Venue` (schema 6305-6325; `Venue` 4265-4274 `{name @unique, slug @unique}`; seeded `alma-avalon`/`st-alma` in `/home/user/alma_suite/packages/db/prisma/seed-prod.ts:45-46`). This is the **only** `@relation` to `Venue` in the schema (1 hit); 78 other models use `venue String` names (Reserve, Marketing, Handbook, settings) and 17 use `venueId` strings without FK. `MenuSnapshot` freezes `venue {id, name, slug}` (`packages/shared/src/menus.ts:141-149`). Templates are bound to venue by slug (`MENU_TEMPLATES[*].venueSlug`, `menu-render.ts:49-70`; `menuTemplatesForVenue` 82-84).

## 7) Gaps — what does not exist yet

1. **No Promotion / WhatsOn / Event model, route or service in the suite API.** Case-insensitive grep for `whatsOn|whats-on|promotion` finds only forecasting (`lib/forecast/accuracy.ts PromotionPolicy`, `import-templates.ts` event_type enum). What's On is a hand-edited TS file in the website repo.
2. **No A5 template, no multi-page support.** `MENU_TEMPLATES` has two A4 à la carte keys (`menu-render.ts:49-70`); the only A5 mention is the comment at line 45. `renderMenuPdf` already takes `{widthMm,heightMm}` (`menu-pdf.ts:139-155`) but the viewport is hard-coded A4 (123), the fill probe assumes one sheet, and publish rejects `pageCount !== 1` (`menu.service.ts:821-828`).
3. **No drinks, functions/set-menu, happy-hour, bottomless or specials templates** (`docs/menu-editor.md:239-245` lists drinks, live screen URL, costing and PDF push to the website as "designed for").
4. **No public endpoint for published menu JSON or PDFs; no fingerprinted/immutable PDF URL.** Website PDFs are hand-copied static files; `alma-functions-menu.pdf` and both bottomless PDFs have no suite counterpart.
5. **`website-menu.service.ts` has no UI caller, no PDF push, and would regress the website** (drops `diet`, resets `image`, ignores `whats-on.ts` and catering `packageGroups`); it writes straight to `main` with a PAT via the Contents API (`env.ts:166-174`). The website's own `scripts/update-website-menu.mjs` duplicates the logic.
6. **No binary image asset model fit for promotion photos.** `MarketingContentAsset` is URL-only with uploads "setup required"; Handbook/GiftCard blobs are purpose-bound; no multer/multipart; JSON body 6mb (~4MB file); GCS lives only in stock-api.
7. **No custom per-event set-menu entity and no link from any menu to an enquiry or reservation.** `SetMenuCourse/Option` are POS/costing constructs on `Recipe`; the Menus `SET_MENUS` section is print-only; `ReserveEnquiry.reservationId/guestId` are never populated; `ReserveReservation` has no package/menu field.
8. **Menu has no kind/date/promotion metadata**: `{venueId, name, templateKey, status, versionCounter}` only (schema 6305-6325); `MenuVersion` adds `heading`, `dietaryNote`, `surchargeLine` (6328-6347). No validity window, no "happy hour 4–6pm" conditions field, no link to a promotion.
9. **Three venue naming schemes** (slug FK in Menus; `venue String` names everywhere else; `avalon`/`freshwater` on the website) with no mapping helper.
10. **Permissions**: menus are not venue-scoped; website publishing requires COMPLIANCE + manager rather than `canPublishMenus`; no Marketing-side permission to publish promotions.
11. **Preview fidelity plumbing**: fonts/logos are two separate copies (API assets vs `menus-web/public`), `MENU_LOGO_FILES` has only the two venue logos — no decorative elements registered; the editor measures fill in a `srcdoc` iframe at A4 px (`MenuPreview.tsx:40-70`).
12. **No rate limiting or caching strategy** for any future public menu/promotion endpoint (only gift-card/reserve public routes are limited today).
